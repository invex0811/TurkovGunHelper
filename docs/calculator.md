# Калькулятор билдов

Код: [`src/domain/calculator/`](../src/domain/calculator/). Публичный вход — [`src/domain/calculator.js`](../src/domain/calculator.js):

```js
import {
  calculateBestBuild,     // подбор билда
  recalculateBuildStats,  // пересчёт характеристик готового набора частей
  calculateAccuracyMoa,   // точность в MOA
  calculateSightingRange, // дальность пристрелки
} from './domain/calculator.js';
```

Калькулятор — чистые функции на JavaScript. Он не зависит от React, DOM и `localStorage`, поэтому работает и в Web Worker, и в тестах на Node.

## Режимы подбора

Пользователь выбирает «цель билда» (`buildGoalMode`). [`buildGoalModes.js`](../src/features/configurator/buildGoalModes.js) переводит её в аргументы калькулятора:

| Цель в UI | `targetType` | `characteristicMode` | Что ищет калькулятор |
| --- | --- | --- | --- |
| **Meta** | `'meta'` | — | Сбалансированный билд: максимум эргономики при минимуме отдачи и веса |
| **Ограничения характеристик** | `'custom'` | `'constraints'` | Билд, который укладывается в желаемые пороги эргономики, отдачи и веса, или ближайший к ним |
| **Приоритеты характеристик** | `'custom'` | `'priorities'` | Лучший билд по упорядоченному списку характеристик или по их весам |

## Входные параметры

```js
calculateBestBuild(
  weapon,                // нормализованное оружие из каталога
  targetType,            // 'meta' | 'custom'
  minErgo,               // желаемая минимальная эргономика (режим ограничений)
  maxRecoil,             // желаемая максимальная вертикальная отдача (режим ограничений)
  modMap,                // catalog.modsById
  options,               // жёсткие условия и политика цен — см. ниже
  customProfile,         // { ergonomics, verticalRecoil, horizontalRecoil, weight, price }
  priorityAttributes,    // порядок, напр. ['recoil', 'ergonomics', 'weight']
  characteristicMode,    // 'constraints' | 'priorities'
  prioritySelectionMode, // 'ordered' | 'weighted'
  priorityWeights,       // { recoil: 50, ergonomics: 30, weight: 20 } — сумма 100
)
```

### `options`

Это **жёсткие** условия: билд, который их нарушает, недействителен.

| Опция | Тип | Смысл |
| --- | --- | --- |
| `maxPrice` | число, `0` = без лимита | Бюджет в рублях |
| `maxWeight` | число, `0` = без лимита | Жёсткий максимальный вес, кг |
| `magazineCapacity` | число | Желаемая ёмкость магазина |
| `requireSuppressor` / `forbidSuppressor` | boolean | Режим глушителя: обязателен, запрещён или на усмотрение калькулятора |
| `sightMode` | `'any'` \| `'reflex'` \| `'scope'` \| `'none'` \| кратность, напр. `'4'` | Какой прицел подходит ([`sightModes.js`](../src/domain/sightModes.js)). Механические, тепловизионные и ночные прицелы не подходят никогда |
| `requireSight` | boolean | Прицел обязателен (`sightMode !== 'none'`) |
| `includeLaser` / `includeFlashlight` | boolean | Нужен ЛЦУ / фонарь |
| `requiredItemIds` | `string[]` | Модули, которые обязательно должны быть в билде |
| `priceMode` | `'pvp'` \| `'pve'` | Режим цен |
| `includeTraderPrices` | boolean | Учитывать предложения торговцев |
| `traderLevels`, `strictTraderLevels` | объект, boolean | Учитывать только доступные по уровню предложения |
| `includeRefOffers` | boolean | Учитывать торговца Ref |
| `includeFleaMarket` | boolean | Учитывать Барахолку; `false` — только торговцы на выбранных уровнях |

Параметры из `customProfile` в режиме ограничений — **мягкие**: они влияют на выбор между допустимыми билдами, но не делают билд недействительным. Желаемый вес (`customProfile.weight`) никогда не превращается в жёсткий `maxWeight`.

## Результат

```js
{
  build: [                     // плоский список установленных частей
    { item, slotName, slotId, slotIndex, slotInstanceId, parentItemId, parentInstanceId },
  ],
  stats: {
    ergonomics,                // 0..100, целое
    recoilModifier,            // суммарный модификатор отдачи, %
    recoilVertical,            // итоговая вертикальная отдача
    recoilHorizontal,
    weight,                    // строка с двумя знаками: '3.42'
    price,                     // рубли или null, если какую-то часть нельзя купить
    accuracyMoa,               // добавляет worker; может быть null
  },
  error,                       // английский текст — билд не найден или нарушены жёсткие условия
  errorCode,                   // напр. 'MAX_PRICE_EXCEEDED'
  errorDetails: [{ code, params }], // по одной записи на каждое нарушенное жёсткое условие
  warnings: [{ code, params, fallback }],
  constraintEvaluation,        // только в режиме ограничений — см. ниже
}
```

Коды предупреждений ([`buildResultMessages.js`](../src/domain/calculator/buildResultMessages.js)) локализуются в UI ([`configuratorNotifications.js`](../src/features/configurator/configuratorNotifications.js)), а `fallback` — английский текст на случай, если перевода нет:

| Код | Значение |
| --- | --- |
| `BASE_WEAPON_MAX_WEIGHT` | Оружие без модулей уже тяжелее лимита |
| `BUILD_MAX_PRICE_EXCEEDED` | Билд дороже бюджета |
| `PRICE_ITEMS_UNAVAILABLE` | У части предметов нет цены при текущей политике цен |
| `MAGAZINE_CAPACITY_SUBSTITUTED` | Магазина выбранной ёмкости нет (например, его не продают на выбранных уровнях), установлен ближайший |
| `REQUIREMENTS_UNMET_CLOSEST_BUILD` | Мягкие ограничения недостижимы — показан ближайший билд |

Коды ошибок (`BUILD_ERROR_CODES` там же) локализуются из `errorDetails` функцией `getLocalizedBuildErrors`; цены и вес форматируются в UI, списки модулей и слотов передаются массивами:

| Код | `params` | Значение |
| --- | --- | --- |
| `SUPPRESSOR_UNAVAILABLE` | — | Глушитель обязателен, но ни один не встаёт |
| `SIGHT_UNAVAILABLE` | — | Нет прицела нужной кратности или типа |
| `LASER_UNAVAILABLE` | — | Лазер включён, но ни один не встаёт |
| `FLASHLIGHT_UNAVAILABLE` | — | Фонарь включён, но ни один не встаёт |
| `REQUIRED_MODULES_MISSING` | `modules` | Обязательные модули не установились |
| `REQUIRED_SLOTS_INCOMPLETE` | `slots` | Обязательные слоты оружия остались пустыми |
| `MAX_PRICE_EXCEEDED` | `maxPrice`, `price` | Билд дороже бюджета |
| `MAX_WEIGHT_EXCEEDED` | `maxWeight`, `weight` | Билд тяжелее лимита веса |

## Формулы характеристик

[`stats.js`](../src/domain/calculator/stats.js):

- **Эргономика** = эргономика оружия + Σ `ergonomicsModifier` частей, округляется и ограничивается диапазоном 0..100.
- **Отдача** = базовая отдача оружия × (1 + Σ `recoilModifier` / 100), отдельно для вертикальной и горизонтальной.
- **Вес** = вес оружия + Σ веса частей.
- **Цена** = цена оружия (`selectWeaponPurchasePrice`) + Σ цен частей (`selectPurchasePrice`) при текущей политике цен. Если хоть одну часть купить нельзя, цена `null`.
- **Точность (MOA)** — по `centerOfImpact` оружия и частей и кривой износа ствола (`deviationCurve`, `deviationMax`). Формула повторяет tarkov-data-manager.
- **Дальность пристрелки** — максимум `sightingRange` среди оружия и установленных прицелов.

## Алгоритм

### Базовый шаг: жадный поиск по слотам

Все режимы строятся на [`_calculateWeighted()`](../src/domain/calculator/candidateSearch.js). Функция получает веса целевой функции и обходит слоты оружия:

1. Слоты сортируются: сначала те, что могут дать обязательный модуль, затем обязательные слоты, затем по таблице `slotPriority` — рукоять, ресивер/крышка/затвор, ствол, газовый блок, цевьё, передняя рукоять, дульное устройство, приклад, магазин, прицел, крепления, рукоятка взведения. Неизвестные слоты идут последними.
2. Для каждого слота перебираются допустимые предметы (`slot.filters.allowedItems`). В слоте магазина остаются только магазины с ёмкостью `magazineCapacity`, а если таких нет — с ближайшей к ней. Для каждого кандидата [`branchEvaluation.js`](../src/domain/calculator/branchEvaluation.js) оценивает **всю ветку**: сам предмет плюс лучшее заполнение его собственных слотов.
3. Отсеиваются ветки, которые конфликтуют с уже установленным (`conflictingItems`), выходят за бюджет или вес с учётом резерва на ещё не заполненные обязательные слоты, ставят второй прицел или неподходящий тип прицела.
4. Если какой-то кандидат слота даёт обязательный глушитель, прицел или обязательный модуль, выбор ограничивается такими кандидатами.
5. Из оставшихся берётся ветка с лучшей оценкой. Необязательный модуль, который не улучшает оценку, не ставится. Исключение — магазин: он нужен всегда.
6. После обхода [`buildOptimizers.js`](../src/domain/calculator/buildOptimizers.js) пересматривает блоки ствола и дульного устройства целиком, а в бюджетном поиске ищет дешёвые улучшения отдачи. Это исправляет типичные ошибки жадного выбора.
7. В конце проверяются жёсткие условия. Нарушения попадают в `error`, мягкие проблемы — в `warnings`.

Оценка ветки в режиме Meta ([`scoring.js`](../src/domain/calculator/scoring.js), `getMetaObjectiveScore`):

```
score = Δэффективной_эргономики × ergoWeight − Σrecoil × recoilWeight − Σweight × weightWeight
```

Эффективная эргономика растёт полностью до `ergoCap` и с коэффициентом `overflowErgoWeight` до `ergoSoftCap`. Поэтому калькулятор не покупает эргономику сверх полезного уровня ценой отдачи.

`calculationCache` ([`calculationCache.js`](../src/domain/calculator/calculationCache.js)) хранит цены, совместимость и минимальные стоимость и вес обязательных подветок. Кэш живёт в пределах одного вызова `calculateBestBuild` и разделяется всеми его внутренними прогонами.

### Meta

- Веса: эргономика 1, отдача 3, вес 15; `ergoCap = 50`, `ergoSoftCap = 70`, `overflowErgoWeight = 0.15`.
- Если задан бюджет (`maxPrice > 0`), дополнительно считается **ценовой** вариант (`PRICE_AWARE_TARGET`): небольшой вес цены, бюджетный поиск, плюс второй прогон с ценой ×20. Он помогает, когда жадный алгоритм потратил бюджет на мелочь и не смог поставить важный приклад. Побеждает вариант с лучшей Meta-оценкой; при равенстве — более дешёвый.

### Ограничения характеристик

[`orchestration.js`](../src/domain/calculator/orchestration.js), ветка `custom` + `constraints`.

Желаемые значения — направленные пороги: эргономика **не ниже**, вертикальная и горизонтальная отдача и вес **не выше**. [`evaluateCustomConstraints()`](../src/domain/customConstraints.js) считает для каждой оси нарушение, нормированное на порог (`|limit|`), и их сумму `totalViolation`. Значение внутри допустимой области даёт 0, как бы далеко оно ни было от порога.

1. `createConstraintSearchRoutes()` строит ограниченный набор **маршрутов**: принудительные варианты для корневых слотов (например, конкретный ствол или приклад) и для вложенных. Каждый маршрут прогоняется через `_calculateWeighted` с подсказками по нарушению (`constraintGuidance`).
2. Всегда считается и обычный прогон без принуждения.
3. Из кандидатов без ошибок выбирается лучший по `compareConstraintCandidates`: меньше суммарное нарушение → выше качество (эргономика − отдача) → дешевле → по ключу состава. Если хоть один кандидат с магазином существует, билды без магазина не участвуют.
4. Если пороги не достигнуты, запускаются запасные поиски: прогоны в пределах желаемого веса, перебор соотношений «эргономика/отдача» (`CONSTRAINT_FALLBACK_SWEEP_STEPS`) и в последнюю очередь Meta-прогон.
5. Если ни один кандидат не валиден, возвращается обычный прогон с его конкретной ошибкой (бюджет, обязательные модули и т. п.). Если валидный есть, но пороги не выполнены, к результату добавляется `REQUIREMENTS_UNMET_CLOSEST_BUILD`.

### Приоритеты характеристик

1. [`generatePriorityCandidates()`](../src/domain/calculator/priorityCandidates.js) строит **пул кандидатов** набором прогонов с разными весами (`getPrioritySearchRoutes()`). Пул не зависит от выбранных приоритетов. С бюджетом добавляются бюджетные маршруты. Жёсткий `maxWeight` в этом режиме не применяется.
2. [`prioritySelection.js`](../src/domain/calculator/prioritySelection.js) нормирует характеристики кандидатов в пределах пула (отдача и вес — меньше лучше, эргономика — больше лучше) и выбирает:
   - **`ordered`** — лексикографически: по первому приоритету остаются кандидаты не хуже лучшего на 10 % нормированного диапазона (`CUSTOM_PRIORITY_RANK_TOLERANCE`), затем по второму и т. д.;
   - **`weighted`** — максимум взвешенной суммы нормированных значений (веса в процентах, сумма 100).
3. При равенстве выбирается более дешёвый билд, затем — по ключу состава.

## Детерминированность

Калькулятор обязан давать один и тот же результат на одном входе: тесты сравнивают конкретные билды. Поэтому:

- при равных оценках решают цена и `getBuildTieKey()` (отсортированные ID предметов);
- нельзя полагаться на порядок ключей объектов из API там, где он влияет на выбор, — сортируйте явно;
- случайность и время в домене не используются.

## Web Worker

[`src/workers/buildCalculator.worker.js`](../src/workers/buildCalculator.worker.js) — модульный worker. Протокол сообщений:

| Сообщение UI → worker | Поля | Назначение |
| --- | --- | --- |
| `initialize` | `modMap`, `modMapVersion` | Передать каталог модулей один раз (он большой) |
| `calculate` | `requestId`, `modMapVersion`, `weapon`, `targetType`, `customProfile`, `priorityAttributes`, `characteristicMode`, `prioritySelectionMode`, `priorityWeights`, `options` | Запустить расчёт |
| `cancel` | `requestId` | Не отправлять результат этого запроса |

Ответы: `{ type: 'result', requestId, result }` или `{ type: 'error', requestId, error: { name, message } }`. Если версия `modMap` не совпадает, worker возвращает `CalculatorWorkerStateError`.

[`buildCalculationWorkerLifecycle.js`](../src/features/configurator/hooks/buildCalculationWorkerLifecycle.js) управляет worker на стороне UI:

- новый расчёт отменяет все незавершённые; синхронный расчёт нельзя прервать изнутри, поэтому старый worker **завершается** (`terminate`) и создаётся новый;
- `modMap` пересылается, только если сменился объект каталога (например, после смены режима цен);
- отменённые промисы отклоняются с `AbortError` — UI их игнорирует;
- падение worker отклоняет все ожидающие запросы.

## Другие потребители калькулятора

- **Цепочки замен** ([`replacementChain.js`](../src/domain/replacementChain.js)). Пользователь меняет модуль в слоте, и калькулятор перезаполняет освободившиеся вложенные слоты через `_calculateWeighted` с параметром `slotFill`. Остальной билд не трогается, а цель та же, что у всего билда.
- **Ручное редактирование** ([`weaponBuildEditor.js`](../src/domain/weaponBuildEditor.js)): `getCompatibleItemsForSlot()` фильтрует совместимые предметы с учётом конфликтов, `planBuildSlotChange()` строит новый набор частей, `validateEditedBuild()` проверяет результат.
- **Стоимость с учётом имеющегося** ([`ownedItems.js`](../src/domain/ownedItems.js)): `calculateBuildCostSummary()` делит цену билда на рыночную, уже оплаченную (отмеченные пользователем предметы) и оставшуюся.

## Как менять калькулятор

1. Сначала напишите тест, который фиксирует ожидаемое поведение ([`tests/calculator/`](../tests/calculator/)).
2. Меняйте веса и пороги только вместе с тестами, которые проверяют сценарий, ради которого делается изменение. Существующие тесты ловят регрессии в других сценариях.
3. Следите за временем работы: калькулятор запускается на каждом нажатии кнопки, а режимы ограничений и приоритетов делают десятки прогонов `_calculateWeighted`. Дорогие шаги запускайте только при необходимости, как это сделано для запасного Meta-прогона.
4. Логика, не связанная с React, должна оставаться в `src/domain/`.
